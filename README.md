# FocusFrame — бронирование фотостудии

Итоговая практическая работа №7. Flutter Web, Supabase Auth и PostgreSQL.

- Приложение: https://kuzyaa1.github.io/up04.01_pr7/
- Исходный код: https://github.com/kuzyaa1/up04.01_pr7
- Панель базы (нужен аккаунт владельца): https://supabase.com/dashboard/project/tphmmplcbjuxdjaspfsy

GitHub Pages размещает Flutter-приложение. Supabase хранит данные и предоставляет Auth и автоматический REST API. Локальный Node-сервер и Render для ПР7 не используются. Папка `server` сохраняет материалы ПР4–ПР6 для сравнения; опубликованная сборка к ней не обращается.

## Запуск

```powershell
flutter pub get
flutter run -d chrome --web-port=5555 --dart-define-from-file=config/supabase.public.json
```

Либо запустить `run-supabase.ps1`, либо выбрать в VS Code конфигурацию **FocusFrame — Supabase** и нажать F5. Интернет нужен для подключения к Supabase.

Вход выполняется по почте. Подготовлены учебные аккаунты `admin@focusframe.local`, `manager@focusframe.local`, `client@focusframe.local`; пароли в репозитории не хранятся. Регистрация создаёт только клиента. Для новых регистраций нужно подтвердить реальную почту по письму Supabase. Администратор меняет роли через раздел пользователей; собственную роль понизить нельзя.

## Схема и роли

Восемь сущностей: залы, фотографы, клиенты, оборудование, бронирования, абонементы, дополнительные услуги, оплаты. Учётные записи хранятся отдельно в Supabase Auth и `profiles`.

| Связь | Реализация |
|---|---|
| 1:1 | Клиент — абонемент: UNIQUE subscriptions.clientId |
| 1:N | Зал — оборудование; клиент — бронирования; бронирование — оплаты |
| M:N | Фотографы — залы; бронирования — фотографы; бронирования — услуги |

| Роль | Возможности | Исключительный раздел |
|---|---|---|
| Клиент | Каталоги, создание собственной брони, продление своей активной брони | Мои бронирования |
| Менеджер | Работа с клиентами, бронями, абонементами и оплатами; просмотр каталогов | Рабочее место менеджера |
| Администратор | Все справочники, архив, восстановление, физическое удаление, пользователи и роли | Пользователи и статистика |

Исключительные разделы недоступны другим ролям, включая администратора. Проверки есть в маршрутах, интерфейсе и SQL API. Клиент не читает чужие бронирования даже по известному идентификатору.

## Предметная особенность

При сохранении PostgreSQL проверяет пересечения интервалов `[начало, конец)` для зала и каждого фотографа, в том числе в разных залах. Соседние интервалы допускаются. Проверка и изменение выполняются в одной транзакции под advisory lock; при конфликте возвращается HTTP 409, исходная запись сохраняется.

Стоимость = аренда зала × часы × (1 − скидка абонемента / 100) + ставки выбранных фотографов × часы + выбранные услуги. Абонемент должен действовать на дату съёмки. Итог и расшифровка сохраняются в бронировании. Переплата запрещена. Время съёмки указывается по Москве.

## API и защита

`lib/core/supabase_api.dart` переводит запросы репозиториев в POST `/rest/v1/rpc/studio_api`. Параметры: `endpoint`, `method`, `query`, `payload`. Функция SQL автоматически доступна через PostgREST, отдельный серверный процесс не требуется.

Все таблицы защищены RLS; прямой доступ `anon` и `authenticated` к таблицам отозван. Разрешён только вызов `studio_api` для `authenticated`. Функция проверяет `auth.uid()`, роль и владельца записи, разрешённые поля, связи и ограничения. Приватные функции не предоставлены клиенту. Роль из метаданных регистрации игнорируется.

Поиск, диапазоны, фильтры, сортировка и пагинация выполняются SQL-запросами. Условия сохраняются в URL. Логическое удаление, восстановление, физическое и групповое удаление обрабатываются в транзакциях. Связанные записи возвращают 409 вместо нарушения целостности.

Валидация возвращает PT422 → HTTP 422 с JSON-ошибками полей; конфликт — PT409 → HTTP 409. Dio отображает ошибки форм, обрабатывает недоступность и таймаут, автоматически обновляет JWT после 401 и повторяет запрос один раз. Сессия хранится между перезагрузками; после выхода токены удаляются.

`config/supabase.public.json` содержит только публичный publishable key, пригодный для браузера. Пароли базы, service_role и secret key в приложение не включаются.

## Развёртывание новой базы

1. Создать проект Supabase.
2. По порядку выполнить в SQL Editor файлы `supabase/migrations/*.sql`. `202610290002_seed.sql` содержит демонстрационные данные, выполнять один раз в новой базе.
3. Обновить публичный URL и publishable key в `config/supabase.public.json`.
4. Создать аккаунты через Authentication → Users. Они получают роль клиента. Владелец базы может назначить первому аккаунту администратора SQL-командой `update public.profiles set role='admin' where email='ВАША_ПОЧТА';`, затем роли меняются через приложение.
5. В Authentication → URL Configuration указать адрес опубликованного приложения как Site URL.

`supabase/tests/bootstrap.sql` используется только локально и в CI для имитации управляемой схемы Auth; в облако его загружать нельзя.

## Проверки и публикация

```powershell
flutter analyze
flutter test
flutter build web --release --no-web-resources-cdn --dart-define-from-file=config/supabase.public.json --base-href /up04.01_pr7/
```

GitHub Actions выполняет форматирование, анализ, все Flutter-тесты, миграции и интеграционные SQL-тесты в отдельном PostgreSQL 17, затем публикует сборку через GitHub Pages. В настройках Pages источник — GitHub Actions. `404.html` содержит приложение с правильным base href, поэтому прямые ссылки на внутренние экраны открываются с сохранением адреса и фильтров.

На момент подготовки: 254 Flutter-теста, включая 9 новых модульных и 5 новых тестов виджетов Supabase. Имеются проверки ширины 360–1920, состояний загрузки/данных/пустого результата/ошибки, прав, валидации, конфликтов и сессии. SQL-тесты проверяют регистрацию без повышения роли, права API, стоимость со скидкой, занятость фотографа, соседние интервалы, атомарность отказа, оплаты и удаление.

Для проверки реального облака: задать переменные окружения `DEMO_ADMIN`, `DEMO_MANAGER`, `DEMO_CLIENT` с паролями учебных аккаунтов и выполнить `node scripts/test-supabase.mjs`. Скрипт создаёт собственные тестовые данные и удаляет только их после проверки. Не запускать с аккаунтами, уже имеющими абонемент: тест создаёт отдельный абонемент для учебного клиента.

## Структура

`lib/models` — модели; `lib/repositories` — доступ к API; `lib/state` — состояние и сессия; `lib/screens` — экраны; `lib/widgets` — формы, таблицы и адаптивные компоненты; `lib/core` — маршрутизация, сеть, права и валидация; `supabase/migrations` — схема и функции; `test` — модульные и виджетные тесты.
